# НТ-Банк — архитектура и план работ

Учебный стенд для практики нагрузочного тестирования (аналог WebTours, но современный).

## Состав стека

| Компонент | Технология | Порт | Память |
|---|---|---|---|
| `bank-app` | Java 21, Spring Boot 3.3, MVC + Thymeleaf + JPA + Security | 8080 | `-Xmx512m` |
| `antifraud-stub` | Java 21, Spring Boot 3.3 (REST-заглушка) | 8081 | `-Xmx128m` |
| `postgres` | PostgreSQL 16 + Flyway-миграции из `bank-app` | 5432 | ~256 МБ |
| `kafka` | Apache Kafka 3.8, KRaft, 1 брокер | 9092 | `-Xmx512m` |
| `prometheus` | Prometheus | 9090 | ~250 МБ |
| `grafana` | Grafana + провижининг дашбордов | 3000 | ~150 МБ |
| `influxdb` | InfluxDB 1.8 (JMeter Backend Listener) | 8086 | ~200 МБ |
| `kafka-exporter`, `postgres-exporter` | exporter'ы для Prometheus | 9308 / 9187 | ~30 МБ |

Сумма лимитов — 4 ГБ, фактически под нагрузкой занято около 1,7 ГБ (замер на этапе 4).
Облегчённый запуск (`--profile lite`): только `postgres` + `bank-app`,
асинхронная обработка переводов — через внутреннюю очередь в памяти.

## Модули bank-app

```
ru.ntbank.bank
├── config        SecurityConfig (2 цепочки: web-сессия + stateless JWT), OpenApiConfig, WebConfig
├── domain        JPA-сущности: AppUser, Account, Card, Operation, Transfer, SmsMessage,
│                 ServiceCatalogItem, Payment, PaymentTemplate, IdempotencyRecord, ExchangeRate
├── repo          Spring Data JPA репозитории
├── service       AccountService, StatementService, TransferService, PaymentService,
│                 TemplateService, SmsService, RegistrationService, ExchangeRateService, SeedService
├── async         TransferDispatcher (интерфейс) → InMemoryTransferDispatcher (этап 1)
│                 → KafkaTransferDispatcher + TransferEventsConsumer (этап 2)
├── client        AntifraudClient → Local (этап 1) / Http (этап 2)
├── security      JwtService, JwtAuthFilter, AppUserDetailsService
├── web           Thymeleaf-контроллеры (страницы)
├── api           REST-контроллеры `/api/v1/**`, `/api/dev/**`, `/api/admin/**`
└── chaos         ChaosSettings, ChaosFilter, RateLimitFilter, LeakStore (этап 3)
```

### Ключевые решения

- **Два контура аутентификации.** Веб: форма входа Spring Security, сессия на cookie `JSESSIONID`,
  CSRF-токен в скрытом поле каждой формы. REST `/api/v1/**`: stateless JWT (HS256),
  access 15 мин, refresh 7 дней, `Authorization: Bearer ...`.
- **Асинхронность за интерфейсом.** `TransferDispatcher` имеет две реализации, выбор по
  `ntbank.async.mode=auto|kafka|memory`. В режиме `auto` приложение на старте проверяет брокер и
  само откатывается на очередь в памяти — поэтому облегчённый профиль работает без правок конфигов.
- **Тестовые данные генерируются SQL-пакетами** (`generate_series`) с одним заранее посчитанным
  BCrypt-хешем на всех пользователей: 1000 пользователей × 2 счёта × 50–200 операций
  поднимаются за секунды, поэтому `POST /api/dev/reset` укладывается в требование «за несколько секунд».
- **`test-data/users.csv`** лежит в репозитории (данные детерминированные) и дополнительно
  перезаписывается приложением при старте в смонтированный том — файл всегда соответствует базе.
- **Idempotency-Key** — таблица `idempotency_record` с уникальным ключом `(user_id, scope, key)`;
  повтор возвращает сохранённый ответ с тем же `transferId`/`paymentId`.
- **Дефекты** — один bean `ChaosSettings` с volatile-полями, применяется на лету:
  задержки/ошибки/CPU/утечка — в сервлет-фильтре по шаблону URL; пул HikariCP — через
  `HikariDataSource.setMaximumPoolSize`; пул Tomcat — через executor коннектора;
  медленный SQL — альтернативный запрос выписки; Kafka — `pause()` слушателя;
  «Антифрод» — проброс настроек в заглушку по HTTP.

## Этапы

1. **Этап 1 — готово.** Банк (веб + REST), PostgreSQL, тестовые данные, `docker-compose`.
   Переводы по телефону с OTP работают через очередь в памяти, «Тестовые СМС» уже есть.
2. **Этап 2 — готово.** Kafka (KRaft), `antifraud-stub`, обработка переводов через топик
   `nt-bank.transfers`, облегчённый профиль `lite` без брокера и внешнего сервиса.
3. **Этап 3 — готово.** Режим «Дефекты»: `/admin/chaos` + `/api/admin/chaos`, rate limit.
4. **Этап 4 — готово.** Prometheus, Grafana с дашбордами «НТ-Банк» и «JMeter + НТ-Банк»,
   InfluxDB 1.8 для JMeter, kafka-exporter и postgres-exporter.

### Как выбирается режим работы (этап 2)

`IntegrationModeResolver` — `EnvironmentPostProcessor`, который до создания контекста
вычисляет два свойства: `ntbank.resolved.async-mode` (kafka | memory) и
`ntbank.resolved.antifraud-mode` (http | local). В режиме `auto` он коротко проверяет
доступность брокера и сервиса. По этим свойствам `IntegrationConfig` поднимает нужные бины,
а консьюмер Kafka вообще не создаётся в режиме памяти — поэтому облегчённый профиль
не пытается подключиться к брокеру и не пишет ошибок в лог.

## Этап 3 — как устроен режим «Дефекты»

Пакет `ru.ntbank.bank.chaos`:

- `ChaosSettings` — состояние всех дефектов, поля volatile, изменения применяются на лету;
- `ChaosTarget` — к каким эндпоинтам применять дефект (фиксированный список);
- `ChaosFilter` — задержка, ошибки 500, нагрузка на CPU, утечка, ограничение частоты.
  Зарегистрирован с порядком 0, то есть после цепочки Spring Security: иначе ограничение
  частоты не знало бы пользователя. Админка, метрики, служебные адреса и статика исключены;
- `LeakStore` — утечка памяти;
- `RateLimiter` — корзина токенов на пользователя, ответы 429;
- `ChaosService` — пулы HikariCP и Tomcat, пауза консьюмера Kafka, проброс настроек
  в «Антифрод», «Выключить всё» и снимок состояния для страницы и REST.

Медленный SQL живёт в `OperationRepository.statementSlow`: условие по `account_id`
завёрнуто в `md5`, поэтому индекс не применяется и база считает хеш для каждой строки.

Две тонкости, на которые напоролся при разработке:

1. `Tomcat.getConnector()` **создаёт** коннектор на 8080, если ни одного не привязано.
   Во время старта Spring Boot временно снимает свои коннекторы, поэтому обращение к нему
   из конструктора бина поднимало второй коннектор и приложение падало с
   «Port 8080 was already in use». Теперь используется `getService().findConnectors()`,
   а штатные размеры пулов снимаются по событию `ApplicationReadyEvent`.
2. Простого `cast(account_id as text)` для «медленного SQL» мало: PostgreSQL уходит
   в параллельный seq scan и укладывается в 40 мс. Хеш на каждую строку даёт честные
   265 мс против 20 мс штатных.

## Этап 4 — мониторинг и что обнаружилось при проверке

Prometheus опрашивает банк, «Антифрод», kafka-exporter и postgres-exporter каждые 5 секунд.
Grafana поднимается с источниками Prometheus и InfluxDB и двумя дашбордами, которые
собираются скриптом `tools/gen_dashboards.py`. Приложение отдаёт свои метрики:
`ntbank_transfers{status}`, `ntbank_transfers_finished_total`, `ntbank_transfer_processing_seconds`,
`ntbank_chaos_active{defect}` (шкала дефектов) и `ntbank_chaos_leaked_bytes`.

Три проблемы, которые нашлись только под нагрузкой:

1. **Флаги дефектов отдавали NaN.** `Gauge` в Micrometer держит слабую ссылку на объект
   состояния; лямбду, переданную как состояние, больше никто не держал, и сборщик мусора
   её удалял. Лечится `.strongReference(true)`. Проверка дашбордов теперь считает NaN
   отсутствием данных — раньше такая серия выглядела как «данные есть».
2. **После OutOfMemoryError банк превращался в «зомби».** Ошибка убивала потоки Acceptor
   и Poller у Tomcat и потоки Kafka, процесс жил, Docker его не перезапускал (он перезапускает
   только завершившийся процесс). Добавлен `-XX:+ExitOnOutOfMemoryError`: теперь контейнер
   поднимается заново примерно за 10 секунд.
3. **Переводы зависали в PROCESSING после перезапуска**, и была возможна двойная обработка.
   Событие в Kafka уходит с задержкой 1–5 секунд из памяти процесса и терялось при остановке;
   а Kafka доставляет «как минимум один раз», и без блокировки строки повторное событие могло
   зачислить деньги дважды. Теперь `process()` берёт перевод через `select ... for update`,
   а при старте `TransferRecovery` досылает переводы, зависшие дольше 30 секунд.

## Аудит после этапа 4 — готово

Найдено и исправлено (каждый пункт проверен на собранном стенде):

1. **История операций без разброса.** У всех клиентов было ~160 операций: `random()` внутри
   `LATERAL` без ссылки на строку PostgreSQL вычисляет один раз. Затем формула от `a.id`
   давала связанные числа у двух счетов клиента (78–172). Теперь число считается в подзапросе
   по строке счёта — после сброса от 50 до 195 операций на клиента.
2. **Dockerfile без Maven Wrapper.** Сборка шла через `mvn` из образа — перешли на `sh ./mvnw`.
3. **Веб-ошибки с кодом 200.** `WebExceptionHandler` теперь ставит настоящий статус:
   404 — чужой/несуществующий перевод, 400 — неверный параметр, 500 — внутренняя ошибка.
4. **Гонка при подтверждении перевода.** 8 одновременных confirm с верным OTP списывали деньги
   до 8 раз (5 из 5 попыток). Перевод берётся через `findByIdForUpdate` — 0 из 5
   (`tools/race_check.py`).
5. **Гонка Idempotency-Key.** 8 одновременных запросов с одним ключом создавали 8 операций
   и семь 500. Теперь ключ сначала занимается (`insert … on conflict do nothing`), остальные
   ждут результата, ошибка ключ освобождает (`tools/idempotency_check.py`, 9/9).
6. **Дефекты переживали перезапуск банка.** После рестарта (например, по OOM) индекс выписки
   оставался удалённым, а заглушка антифрода — сломанной, хотя страница показывала «выключено».
   При старте индекс восстанавливается, дефекты заглушки сбрасываются.
7. **Ошибки форм — плашкой сверху.** ТЗ просит рядом с полем: `FormErrors` раскладывает
   коды ошибок по полям форм перевода и оплаты.
8. **Конвертация теряла копейки.** 9 250 ₽ превращались в $ 99,90 из-за промежуточного
   округления — считаем через рубли с одним округлением в конце.
9. **Одновременная регистрация одного логина — 500.** Проверка «логин свободен» проходила
   у обоих запросов, второй падал на уникальном индексе. Нарушение уникальности теперь
   `409 LOGIN_TAKEN` и сообщение в форме.
10. **Разный формат ошибок REST.** 401/403 от безопасности писались вручную, 429/500 режима
    «Дефекты» — в формате Spring Boot. Все идут через `ApiErrorWriter` в формате `ApiError`
    (коды `UNAUTHORIZED`, `INVALID_TOKEN`, `WRONG_TOKEN_TYPE`, `FORBIDDEN`, `RATE_LIMITED`,
    `CHAOS_ERROR`).
11. **Сброс данных под нагрузкой падал с 500.** TRUNCATE брал блокировки по одной таблице и
    вставал во взаимоблокировку с переводом, который держал `transfer` и ждал `operation`.
    Повторы с `lock_timeout` помогали лишь отчасти (под 30 потоками — до 37 попыток, иногда
    не хватало). Теперь сброс идёт через `DataResetGate`: справедливая read/write-блокировка
    в приложении, запросы (фильтр с порядком -101) и обработка переводов (Kafka и очередь
    в памяти) берут её на чтение, сброс — на запись. Под нагрузкой 30 потоков 8 сбросов подряд —
    все по 3,5 с, ни одной взаимоблокировки. `lock_timeout` с повторами оставлен на случай
    посторонних соединений.
12. **Флакающая проверка «Нет индекса».** `chaos_check` читал `pg_stat_user_tables` раньше, чем
    PostgreSQL сбрасывает счётчики (~10 с), — ждём 11 с.

Итоговый прогон: `audit_check` 49/49, `smoke_test` 29/29 (и в облегчённом профиле),
`chaos_check` 23/23, `idempotency_check` 9/9, `race_check` 0 повторных списаний из 5,
`check_dashboards` — 71 запрос с данными под нагрузкой, `dashboard_defects_check ошибки частоты`
2/2; одновременная регистрация одного логина из 8 потоков — один успех и 7 понятных ошибок;
все 23 страницы (клиент, админ, ошибки, пустые состояния, форма с ошибкой у поля)
без горизонтальной прокрутки на 360 px.

## Повторный аудит — готово

Свежий проход по коду и граничным случаям (`tools/edge_check.py`, 29 проверок). Найдено и исправлено:

1. **500 на длинных полях.** Комментарий к переводу (> 160), лицевой счёт (> 40), название шаблона (> 80),
   длинный `Idempotency-Key` упирались в длину колонки. Теперь проверки в `Inputs` — `400` с понятным
   текстом, в вебе ошибка у поля.
2. **Списание без платежа.** Оплата с «сохранить шаблон» шла двумя транзакциями: если шаблон не
   сохранялся, деньги уже были списаны, а клиент видел ошибку (и повтор с тем же ключом списывал снова).
   Теперь оплата и шаблон — одна транзакция, название шаблона проверяется до оплаты.
3. **Повтор платежа по шаблону игнорировал `Idempotency-Key`** — тот же ключ давал второй платёж.
4. **Суммы с тремя знаками после запятой** (`0.001`, `100.555`) принимались и молча округлялись базой.
5. **1 копейка в доллары** списывала рубли и зачисляла $ 0,00 — теперь `400 AMOUNT_TOO_SMALL`.
6. **Веб-формы не принимали «100,50»** (страница 400) и пустую сумму — теперь запятая допустима,
   пустая сумма — ошибка у поля. После ошибки форма сохраняет выбранный счёт, комментарий, шаблон.
7. **OTP:** третья неверная попытка только уменьшала счётчик, перевод отклонялся лишь при четвёртой.
   Теперь третья сразу даёт `409 OTP_ATTEMPTS_EXCEEDED`, в ошибке видно, сколько попыток осталось.
   Для отклонённого перевода текст «Перевод уже подтверждён» заменён на «Перевод нельзя подтвердить».
8. **Регистрация с ФИО длиннее 60 символов — 500**: держатель карты был `varchar(60)`. Миграция V3.
   Ошибки «логин занят» / «телефон занят» / неверный телефон — теперь у своего поля.
9. **Ошибки REST до контроллеров** — 404 (неизвестный адрес), 405 (не тот метод), 401 Basic в админке —
   шли в формате Spring Boot; 415 (не JSON) давал 500. Теперь всё в формате `ApiError`
   (`ApiErrorAttributes` + обработчики), тексты по-русски вместо `JSON parse error: …`.
10. **Ссылки пагинации каталога и выписки** не кодировались: `&`, `#`, пробел в поиске ломали ссылку.
11. **Пул HikariCP в «Дефектах» до 200** при 100 соединениях PostgreSQL — ограничен 90.
12. **Банк «готов» раньше данных.** `/actuator/health` и healthcheck давали UP за ~4 с до создания
    тестовых пользователей. Теперь readinessState входит в health: пока идёт генерация — 503.

Проверено запуском с нуля: `build --no-cache` (5 мин) и `up` на пустых томах отдельного проекта
`ntbankclean`, данные основного стенда не тронуты. Prometheus — 5/5 целей up, Grafana — оба дашборда
и оба источника, Kafka — топик на 3 раздела, `users.csv` — 1000 строк. Облегчённый профиль с нуля —
так же (около 470 МБ памяти). Основной стенд после этого поднят на старых томах — миграция V3
применилась к существующей базе.

Итоговый прогон: `audit_check` 50/50, `edge_check` 29/29, `smoke_test` 29/29 (в облегчённом — 27/27,
без проверок «Антифрода»), `chaos_check` 23/23, `idempotency_check` 9/9, `race_check` 0 из 5,
`dashboard_defects_check` — 12 из 12 дефектов видны на дашборде. В полном прогоне последний шаг
(429) показал 0: фоновые клиенты скрипта не обновляли токен, через 15 минут получали 401 —
скрипт исправлен (вход заново раз в 10 минут), шаг перепроверен отдельно: 122 ответа 429 в секунду.

## Третья проверка — готово

Новое: `tools/outage_check.py` (настоящие отказы контейнеров), сквозной прогон JMeter 5.6.3.

1. **Деньги «зависали» при недоступной Kafka.** Отправка события асинхронная, ошибка приходила
   в callback и терялась: перевод, подтверждённый во время сбоя, навсегда оставался «В обработке» —

## Часовой тест надёжности — готово

JMeter 5.6.3, веб-сценарий в пропорциях профиля на 70%, 150 потоков, час, Backend Listener
(`ntbank-soak` на дашборде «JMeter + НТ-Банк»). Утечка — цель «Вход»: 4 КБ, через 10 минут по
процедуре README поднята до 12 КБ.

- 938 тысяч запросов (487 тысяч сэмплов верхнего уровня), профиль выдержан: 10,2 входа, 10,2 просмотра,
  10,2 выписки, 6,8 перевода, 10,2 оплаты, 3,4 выхода в секунду.
- Живые данные после GC: 60 → 486 МБ из 512, ровный рост; сессии — плато ~12,9 тыс. через 30 минут.
- 55 минут p95 стабилен (вход ~120 мс, выписка ~40 мс), затем шторм полных GC: ~180 в минуту, 23% времени
  в GC, p95 транзакций 8–17 с, пропускная способность 179 → 151 запрос/с. OOM в пределах часа не случился.
- «Выключить всё» освободило heap без перезапуска (живые данные 87 МБ), ответы снова за ~10 мс.
- 30 ошибок (0,01%) — «Нельзя перевести самому себе»: план выбирал получателя случайно, иногда это
  был сам отправитель. Ошибок банка нет.
- Деньги: 24 462 подтверждённых перевода = списания, 22 813 выполненных = зачисления,
  1 649 отклонённых = возвраты, 36 476 платежей = списания; расхождений по счетам 0.

**Найдено в документации:** таблица подбора утечки в README считала 20 запросов в секунду на `/login`,
а их ~10 — `POST /login` обрабатывает Spring Security до фильтра дефектов. С 4 КБ heap заполнился бы
за ~2 часа, а не за час. Таблица пересчитана по замеру (10 КБ ≈ час, 3 КБ ≈ три часа), добавлены
веб-сессии как «ложная утечка» первых 30 минут и описание шторма GC перед OOM.
